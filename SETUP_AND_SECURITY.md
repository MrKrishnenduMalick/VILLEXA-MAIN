# VILLEXA — Setup, Security Architecture & Administration Guide

This guide documents the persistent architecture, database migrations, Row-Level Security (RLS) policies, storage validation, and admin provisioning for the Villexa furniture showroom.

---

## 1. Initial Architecture & Security Principles

1. **Explicit Admin Authorization:**
   * A normal authenticated Supabase user is **never** granted administrative rights automatically.
   * Administrative access requires an entry in the `app_admins` table matching `auth.uid()`, enforced via the PostgreSQL security-definer function `is_admin()`.
   * **There is no public admin registration form.**
2. **Database-Level Isolation:**
   * Public visitors can only execute `SELECT` queries on `products` where `status = 'published'`, `collections` where `is_published = true`, and their associated media.
   * Public visitors can submit `enquiries` (`INSERT`), but RLS strictly forbids public users from querying (`SELECT`), updating, or deleting existing enquiries.
   * Draft products, private quotations, and administrative metadata are inaccessible to public visitors, even if direct HTTP API calls are attempted.
3. **Dual-Tier Storage Architecture & Draft Asset Protection:**
   * **Private Staging Vault (`atelier-vault`):** Declared with `public = false`. All uploaded draft photographs, 3D GLB models, and 360-degree sequences land here first. Direct public CDN access returns `404/403`. Previews are accessed solely via short-lived signed URLs (`createSignedUrl`, 3600s) generated by authorized administrators.
   * **Public Showroom Buckets (`product-images`, `product-models`, `showroom-videos`, `360-sequences`):** Only assets of **published** creations are promoted into these buckets.
   * **Immediate Revocation on Unpublish:** When a product is transitioned back to `draft` or deleted, its public copies in showroom buckets are **deleted**, immediately revoking public CDN access.
4. **Zero Client Secret Leakage:**
   * The browser application bundles only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`.
   * The `SUPABASE_SERVICE_ROLE_KEY` is **never** placed in client code or `.env.example`.

## 2. Storage Buckets & Access Control Matrix

| Bucket Identifier | Bucket Visibility | Purpose | Access Strategy | RLS Write / Delete |
| :--- | :--- | :--- | :--- | :--- |
| `atelier-vault` | **Strictly Private** (`public: false`) | Staging draft images, 3D GLB models, 360 frames | Short-lived signed tokens (`?token=...`, 3600s) for authorized admins | `is_admin()` only |
| `product-images` | **Public** (`public: true`) | High-res photography of **published** pieces | Permanent CDN URL; promoted only on publish | `is_admin()` only |
| `product-models` | **Public** (`public: true`) | Self-contained `.glb` 3D models of **published** pieces | Permanent CDN URL; promoted only on publish | `is_admin()` only |
| `showroom-videos`| **Public** (`public: true`) | Showroom atelier walkthrough videos | Permanent CDN URL; managed via site settings | `is_admin()` only |
| `360-sequences`  | **Public** (`public: true`) | Turntable photographic frames of **published** pieces | Permanent CDN URL; promoted only on publish | `is_admin()` only |

> **Note on 3D Model Formats:** To guarantee reliable rendering in Three.js WebGL without missing buffer or texture dependencies, uploads require self-contained `.glb` binary containers. Standalone `.gltf` files referencing external `.bin` buffers or separate image paths cannot be hosted as single assets and are rejected by client validation.

## 3. Asset Lifecycle: Draft Staging, Publication & Revocation

```
[Admin uploads media in Editor]
            │
            ▼
┌───────────────────────────────┐
│ Upload to `atelier-vault`     │  <-- Bucket is private (`public = false`)
│ Generate 1-hour signed URL    │  <-- Accessible ONLY by authorized administrator
└───────────────┬───────────────┘
                │
                ├──────────────────────────────────────┐
                ▼ (If "Save as Draft")                 ▼ (If "Publish to Showroom")
┌───────────────────────────────┐      ┌──────────────────────────────────┐
│ Persist vault path in DB      │      │ Promote asset to showroom bucket │
│ NO public CDN URL created     │      │ Generate permanent public CDN URL│
│ Public access remains 404/403 │      │ Set `products.status='published'`│
└───────────────────────────────┘      └────────────────┬─────────────────┘
                                                        │
                                                        ▼ (If Admin later unpublishes product)
                                       ┌──────────────────────────────────┐
                                       │ Delete file from showroom bucket │
                                       │ Public CDN URL immediately 404s  │
                                       │ Asset remains safe in vault      │
                                       └──────────────────────────────────┘
```

### Caching and URL Revocation Details:
1. **Origin Invalidation:** Deleting an asset from the public showroom bucket ensures all subsequent requests to the Supabase Storage origin return `404 Not Found`.
2. **Intermediate CDN / Browser Cache:** Assets are uploaded with `cache-control: max-age=3600`. If an external user loaded the asset immediately prior to unpublishing, their local browser cache may retain the cached binary for up to 1 hour. However, no new visitor or uncached request can fetch the unreleased asset.
3. **Unique Path Hashing:** Every uploaded asset path embeds a unique timestamp and random salt (`${Date.now()}_${random}_${filename}`). Re-publishing creates a completely fresh URL, eliminating stale cache collisions.

## 4. Enquiry Security & Spam Protection

Customer enquiries submitted via the public contact form and product inquiry buttons are protected by multi-layered validation:

1. **Database-Level RLS Check Constraint:**
   ```sql
   WITH CHECK (
     length(trim(full_name)) BETWEEN 2 AND 100 AND
     length(trim(email)) BETWEEN 5 AND 255 AND
     email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$' AND
     length(trim(message)) BETWEEN 5 AND 5000 AND
     status = 'new'
   );
   ```
   * Enforces RFC-compliant email syntax via PostgreSQL regex.
   * Rejects oversized payloads (>5,000 chars) to prevent storage exhaustion attacks.
   * Forces `status = 'new'` on submission, preventing callers from marking enquiries as reviewed or archived.
2. **Strict Select Privacy:**
   * `SELECT`, `UPDATE`, and `DELETE` on `enquiries` require `is_admin()`. Unauthenticated visitors and non-admin authenticated users can **never** read or enumerate existing enquiries.

## 5. Step-by-Step Setup & Migration Instructions

### Step 1: Create a Free Supabase Project
1. Log into [Supabase Dashboard](https://supabase.com).
2. Create a new project (e.g., `villexa-showroom`).
3. Select your preferred region (e.g., Frankfurt/Milan for Europe or US East).

### Step 2: Execute Database Migrations (In Exact Order)
In your Supabase project dashboard, navigate to **SQL Editor**:

1. **First, execute Migration 001 (`supabase/migrations/001_complete_schema_and_security.sql`):**
   * *Note on Filename:* The verified base migration file is `001_complete_schema_and_security.sql` (any reference to `001_initial_schema.sql` refers to this file).
   * Open or copy the full contents of `001_complete_schema_and_security.sql` into the SQL Editor and click **Run**.
   * This creates:
     * Extensions: `pgcrypto`.
     * Admin Authorization: `app_admins` table and `is_admin()` SECURITY DEFINER function.
     * Core Tables: `categories`, `collections`, `products`, `product_media`, `product_finishes`, `product_sequences_360`, `site_settings`, `enquiries`.
     * Storage Buckets: `atelier-vault` (private, 100MB quota), `product-images` (public, 15MB quota), `product-models` (public, 50MB quota), `showroom-videos` (public, 100MB quota), `360-sequences` (public, 15MB quota).
     * Row Level Security: Enforces strict RLS policies on every table and bucket.

2. **Next, execute Migration 002 (`supabase/migrations/002_media_and_taxonomy_enhancements.sql`):**
   * Open or copy the full contents of `002_media_and_taxonomy_enhancements.sql` into the SQL Editor and click **Run**.
   * This enhances the schema idempotently:
     * Adds `cover_image_url` to `categories` for visual banners.
     * Adds `video_url` and `video_poster_url` to `collections` for suite video walkthroughs.
     * Adds `thumbnail_url` to `product_media` for video poster thumbnails.
     * Inherits existing RLS policies without modification.

3. **Next, execute Migration 003 (`supabase/migrations/003_preferred_viewer_video_support.sql`):**
   * Open or copy the full contents of `003_preferred_viewer_video_support.sql` into the SQL Editor and click **Run**.
   * Safely updates `products_preferred_viewer_check` on the `products` table:
     * Drops existing check constraint if present (`products_preferred_viewer_check`).
     * Re-creates the constraint accepting `('gallery', 'glb_3d', 'sequence_360', 'video')`.
     * Preserves default `'gallery'` and all existing data.

### Step 3: Initial Admin Account Provisioning
1. Navigate to **Authentication > Users** in the Supabase Dashboard.
2. Click **Add User > Create User**. Enter your administrative email and a strong password (e.g. `admin@villexa.com`).
3. Copy the generated **User UID** (e.g., `c27d49e1-8840-4f9e-996c-b3a985e5d321`).
4. Go to **SQL Editor** and run the provisioning query (specifying the `'admin'` or `'super_admin'` role):
   ```sql
   INSERT INTO app_admins (user_id, email, role)
   VALUES ('<YOUR_USER_UID>', '<YOUR_EMAIL>', 'admin');
   ```
5. Your account is now explicitly authorized. You can log into `/admin` through the portal.

### Step 4: Configure Local Environment
1. Copy `.env.example` to `.env`:
   ```bash
   cp .env.example .env
   ```
2. Populate `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` from **Project Settings > API**.
3. Restart the Vite development server (`npm run dev`).
